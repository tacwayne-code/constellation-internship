## 1. 项目概述

### 1.1 项目定位

**紧急采购看板**（目录名「采购看板」）是一个**只读**的采购驾驶舱（Dashboard）项目，仿照内部 `ERP看板` 的驾驶舱风格精简而来，**只保留一个业务模块：紧急未采购订单**。

它把 Odoo ERP 中「被标记为紧急、但尚未转为正式采购订单（即仍未采购）」的采购单 / 询价单（RFQ）实时呈现在一块大屏风格的看板上，让采购管理者**打开一眼就能知道今天有哪些紧急采购必须处理**。

### 1.2 设计原则

| 原则 | 说明 |
| --- | --- |
| **严格只读** | 后端仅调用 Odoo 只读方法（`search_read` / `search_count` / `read` / `fields_get` / `name_search` / `search`），不提供任何新增、修改、删除、审批、确认或写回 Odoo 的能力 |
| **零依赖** | 后端使用 **Python 标准库**实现（无需 `pip install` 任何第三方包）；前端为原生 HTML/CSS/JS，无构建工具、无框架 |
| **开箱即用** | Windows 下双击 `启动.bat` 即可启动，浏览器访问即用 |
| **安全优先** | 默认只监听本机、静态文件白名单、服务器指纹隐藏、错误信息脱敏、可选访问令牌（详见[第 8 章](#8-安全设计)） |
| **体验兜底** | Odoo 不可达时自动回退「本地缓存 → 示例数据」，页面不空白 |

### 1.3 目标用户与使用场景

- **采购负责人 / 采购员**：每日晨会或大屏轮播查看「今天必须处理」的紧急单。
- **管理者**：查看待采购金额、涉及供应商、平均等待天数等汇总指标。
- **适用场景**：办公室大屏、个人电脑浏览器、局域网共享（可选）。

## 2. 功能特性

### 2.1 核心功能

- **紧急未采购单展示**：只展示 Odoo 中标有「紧急」且状态仍为「询价 / 已发送 / 待审批」（未转采购订单）的单据。
- **P0 ~ P3 四级紧急度**：按预计日期（`date_planned`）自动分级并着色（详见 4.4）。
- **自动刷新**：页面每 3 分钟自动同步一次；手动点「刷新」立即拉取最新数据。
- **等级筛选 + 关键词搜索**：按 P0~P3 筛选；搜索模糊匹配单号 / 供应商 / 采购员 / 物料 / 状态 / 预计日期。
- **多维明细查看**：点击色块弹出完整详情（基础字段 + 物料明细 + 处理原因 + 处理建议）。
- **关键指标 KPI**：紧急单总数 / 今日必须处理 / 已超期 / 待采购金额 / 涉及供应商 / 平均等待。
- **供应商金额排行**：紧急单按金额排序的 Top 8 供应商。
- **状态分布数据**：接口返回各单据状态（询价单 / 已发送 / 待审批）的数量与颜色（当前界面布局未单独展示该面板，数据保留供扩展）。
- **看板速览**：三段式中文摘要（总数、超期与金额概况、只读提示；当前布局未展示，数据保留供扩展）。

### 2.2 健壮性特性

- **三级数据兜底**：Odoo 在线 → 本地缓存（localStorage，7 天过期）→ 内置示例数据。
- **并发保护**：后端单飞（single-flight）刷新，多请求并发时复用同一次 Odoo 拉取，不击穿。
- **限流拉取**：分页拉取 Odoo 数据（每页 500 条），并设有订单数量上限，避免大表全量加载。

### 2.3 大屏能力

- 一键全屏（右上角 ⛶ 按钮）。
- 深色驾驶舱主题：深蓝背景 + 网格纹理 + 霓虹光效，适合投影/大屏。
- 时钟实时显示。

### 3.4 数据流（一次完整刷新）

1. 浏览器定时（3 分钟）或手动触发 `loadRealDashboard()`，请求 `/api/urgent-orders`。
2. `server.py` 先查内存缓存：缓存未过期直接返回，避免反复打 Odoo。
3. 缓存过期且无其他线程在刷新时，创建 `OdooClient` → 认证（`/web/session/authenticate`）→
   探测/解析紧急域 → 分页拉取 `purchase.order` → 按订单 id 批量拉取 `purchase.order.line`。
4. 后端组装 KPI、订单、状态分布、供应商排行、速览文案，写入缓存并返回 JSON。
5. 前端更新 `rawData` → 重渲染（色块墙 / 明细表 / 排行 / 状态条）→ 写入 localStorage 缓存。
6. 拉取失败 → 读 localStorage 缓存；缓存也没有 → 用内置示例数据，状态条标注数据来源。

## 4. 数据模型与业务规则

### 4.1 数据源模型

| Odoo 模型 | 使用方式 | 读取字段 |
| --- | --- | --- |
| `purchase.order` | `search_read` 分页 | `id` `name` `partner_id` `user_id` `amount_total` `state` `date_order` `date_planned` `currency_id` |
| `purchase.order.line` | `search_read` 分页（按订单 id 过滤） | `order_id` `product_id` `name` `product_qty` `qty_received` `price_unit` `product_uom` `state` |

> 拉取有上限保护：订单数量上限与物料行数量上限均为可配置环境变量（见 7.2 的 `DASHBOARD_MAX_ORDERS`）。

### 4.2 紧急标记如何识别（按优先级）

看板只展示「紧急」单据，识别逻辑按以下优先级：

1. **`ODOO_URGENT_DOMAIN`（最高优先）**：配置了完整 Odoo 域表达式（JSON）时完全以它为准，例如 `[["x_studio_urgent","=",true]]`。
2. **指定字段 `ODOO_URGENT_FIELD`**：按字段类型分别处理：
   - **布尔字段**：过滤条件 `字段 = true`；
   - **选择（selection）字段**（如 Odoo 18 的 `priority`，存储值是 key `"0"/"1"`）：调用 `fields_get` 取选项，按选项 label 包含「紧急 / urgent」（不区分大小写）匹配出对应 key，再用 `字段 in [key]` 过滤——**这是 Odoo 18 selection 字段的关键兼容点**；
   - **文本/字符字段**：按「包含紧急标签或 `urgent` 或等于 `true`」三条件（OR）过滤。
3. **自动探测字段**：未指定字段时，依次探测 `x_studio_urgent` → `x_urgent` → `urgent` → `x_studio_is_urgent` → `x_studio_priority` → `priority`，命中即用。
4. **兜底**：以上均找不到紧急字段时，按「单号（`name`）包含『紧急』」识别。

> 紧急标签文本 `ODOO_URGENT_TAG` 用于文本/选择型字段的匹配关键词，可自定义。

### 4.3 未采购（紧急）状态

- 默认只纳入状态为「询价 / 已发送 / 待审批」的单据，即尚未转为确认采购订单。
- 状态集合可通过 `ODOO_URGENT_STATES`（JSON 数组）自定义。
- 单据状态的中文映射（订单级）：

| Odoo 状态 | 中文显示 |
| --- | --- |
| `draft` | 询价单 |
| `sent` | 已发送 |
| `to approve` | 待审批 |
| `purchase` | 采购订单 |
| `done` | 已完成 |
| `cancel` | 已取消 |

物料明细行状态映射（前端 `LINE_STATE_TEXT`）：`draft`→询价单、`purchase`→采购中、`done`→已完成、`cancel`→已取消。

### 4.4 紧急等级（P0 ~ P3）判定规则

| 等级 | 含义 | 判定条件（基于 `date_planned` 与当前日期） |
| --- | --- | --- |
| **P0** | 今天必须处理 | 已超期（超期天数 > 0）**或** 今天到期（距预计 0 天） |
| **P1** | 3 天内处理 | 距预计日期 ≤ 3 天 |
| **P2** | 本周关注 | 距预计日期 4 ~ 7 天 |
| **P3** | 普通提醒 | 其余紧急未采购单 |

对应颜色（前端 `LEVEL_META` 与 CSS 变量）：

| 等级 | 颜色 | 说明 |
| --- | --- | --- |
| P0 | 暗红（`#b91c1c` 系） | 醒目但不刺眼（曾多次按用户要求调暗） |
| P1 | 橙（`#f97316`） | 尽快确认转采购 |
| P2 | 黄（`#eab308`） | 本周关注 |
| P3 | 蓝（`#38bdf8`） | 普通提醒 |

### 4.5 派生指标

| 指标 | 计算方式 |
| --- | --- |
| 等待天数 `daysWaiting` | 今天 − 下单日期（`date_order`），取非负 |
| 超期天数 `daysOverdue` | 预计日期（`date_planned`）早于今天的天数，未超期为 0 |
| 距预计天数 `daysToPlanned` | 今天到预计日期的天数；未设置预计日期时为空 |
| 预计文案 `plannedText` | 「超期 N 天」/「今天到期」/「N 天后到期」/「未设置预计日期」 |
| 待收数量 `remaining` | 订购数量 − 已收数量（`product_qty − qty_received`），不小于 0 |
| 物料清单 `materials` | 从物料显示文本 `[编码] 名称` 中解析名称，去重后最多展示 3 个，并统计总数 |
| 平均等待 `avgWaiting` | 所有等待天数 > 0 的订单的算术平均（保留 1 位小数） |
| 金额 `amount` | `amount_total` 合计；显示为 `¥x,xxx.xx` 格式（前端金额工具 `moneyText()` 对 ≥1 万的单价等场景简写为「¥x.x万」） |

## 5. 模块详细说明

### 5.1 后端 `server.py`（652 行，零第三方依赖）

按职责划分为以下模块：

| 模块 | 职责 |
| --- | --- |
| **环境加载** `load_env_file()` | 标准库解析 `.env`（支持 `#` 注释、单/双引号值）；**已存在的系统环境变量优先，不覆盖**；非法整数 / JSON 值打印 ⚠️ 并回落默认值（`_env_int()` 容错） |
| **OdooClient** | JSON-RPC 客户端：`CookieJar` 保持会话；`authenticate()` 走 `/web/session/authenticate`；`call_kw()` 走 `/web/dataset/call_kw/{model}/{method}`，**方法名白名单校验**（非只读方法直接拒绝）；网络层 3 次重试（502/503/504 与连接超时，退避 1.5s×次数），单请求超时 25s |
| **紧急域解析** `resolve_urgent_domain()` | 按 4.2 的优先级组装「紧急」过滤条件，兼容 boolean / selection / 文本三类字段 |
| **数据组装** `build_urgent_orders()` | 拉取订单 + 物料行 → 计算派生指标 → 生成 KPI / 订单列表 / 状态分布 / 供应商排行 / 速览文案 |
| **缓存与并发** `build_dashboard()` | 内存缓存（TTL 可配）；单飞刷新（`_REFRESHING` 标志 + 双检锁）：等待线程**不持锁**等待（最多 20 秒），避免首次并发刷新死锁 |
| **HTTP 服务** `DashboardHandler` | 基于 `ThreadingHTTPServer`：静态文件白名单、API 路由、访问令牌校验、响应头控制、服务器指纹隐藏 |
| **启动入口** `main()` | 读取 `HOST` / `PORT` 启动，打印启动信息（服务地址、监听地址、紧急标记配置、令牌状态） |

关键常量与状态：

- 只读方法白名单：`search_read` / `search_count` / `read` / `fields_get` / `name_search` / `search`
- 静态文件白名单：`/` `/index.html` `/styles.css` `/app.js`
- 状态与颜色映射：见 4.3 与 4.4
- 缓存：`_CACHE`（数据 + 时间戳）+ `_CACHE_LOCK` + `_REFRESHING` 单飞标志

### 5.2 前端 `app.js`（851 行，原生 JS）

| 模块 | 职责 |
| --- | --- |
| **数据状态** | `rawData`（当前看板数据）、`levelFilter`（等级筛选）、`searchTerm`（搜索词）、`expandedOrderId` / `selectedOrderId`（明细展开/选中）、`displayLimit`（色块墙分页，默认 20） |
| **兜底数据** | `fallbackData`（空模板）+ `buildDemoData()`（7 条示例单，覆盖 P0~P3 各等级，用于完全离线时预览） |
| **本地缓存** | localStorage 存「上次成功数据」，**7 天过期**自动清理；启动时先读缓存渲染再请求线上 |
| **访问令牌** | `getAccessToken()`：URL `?token=`（自动存入 localStorage）> localStorage；`apiUrl()` 自动拼接 `token` 参数 |
| **筛选与搜索** | `filteredOrders()`：先按等级过滤，再对 单号/供应商/采购员/状态文案/预计文案/物料/明细行 做归一化（转小写、去空格）模糊匹配 |
| **排序** | `sortOrders()`：等级（P0→P3）→ 超期天数降序 → 等待天数降序 |
| **渲染函数** | `ScreenTitleStrip` / `RiskKpiCard`（6 张 KPI 横排）/ `RiskTileWall`（色块墙，每页 20 可「查看更多」）/ `RiskTopTable`（明细表，最多 60 行，行内展开「Odoo 依据」）/ `SupplierRanking`（供应商排行）/ `SummaryBar` / `LevelBars`（后两者当前布局未使用，保留向后兼容） |
| **详情弹窗** | `openOrderDetail()`：基础字段表 + 物料明细表（数量/已收/未收/单价/状态）+ 处理原因 + 处理动作；ESC / 点遮罩 / ✕ 关闭 |
| **交互绑定** | `bindControls()`：等级下拉、搜索框、刷新、全屏、使用说明、弹窗、色块/行点击（事件委托） |
| **刷新调度** | 启动即拉取；`setInterval` 每 3 分钟拉取一次（走服务端缓存）；手动刷新强制 `nocache=1` 绕过缓存；`refreshingDashboard` 标志防并发 |

> 安全细节：所有动态文本经 `escapeHTML()` 转义后再插入 DOM，防止 XSS。

### 5.3 页面结构 `index.html`（196 行）

- **顶部命令栏**：品牌标识 + 标题、等级筛选下拉、搜索框、刷新、使用说明、全屏。
- **状态条**：连接状态圆点、数据来源文案、最后同步时间、数据覆盖统计、实时时钟。
- **看板容器** `#urgentLayout`：由 app.js 动态渲染。
- **使用说明弹窗**（8 节）：这是什么 / 紧急等级颜色 / 界面布局 / 数据来源与判定方式 / 配置与凭证 / 数据刷新与缓存 / 搜索与筛选 / 交互操作。
- **详情弹窗**：订单明细（标题 + 内容区，内容超长内部滚动）。
- **Toast 提示**：刷新结果提示。
- **缓存破更新**：CSS/JS 以唯一时间戳版本号引用（`?v=<unix时间戳>`），保证改版后浏览器必然重新下载。

### 5.4 样式 `styles.css`（1540 行）

- **主题**：深色驾驶舱。CSS 变量定义配色（背景 `#0b1220` 系、P0~P3 等级色、边框、文字层级）；背景为深蓝渐变 + 网格纹理 + 霓虹光晕。
- **布局**：`.factory-screen` 为两列四行网格（详见下表），满屏高度，各区域独立滚动。
- **响应式**：断点 1320px（降为单列堆叠、KPI 3 列、色块 2 列）、720px（KPI 2 列、色块 1 列）。

健康检查，无需 Odoo 连接：

```json
{ "ok": true, "source": "local" }
```

启用访问令牌时同样需要携带令牌。

### 6.3 访问令牌校验规则

- 未配置 `BOARD_ACCESS_TOKEN`：`/api/*` 全部放行（适合纯内网可信环境）。
- 已配置：请求必须满足其一，否则返回 **401**：
  - URL 查询参数 `?token=<令牌>`；
  - 请求头 `Authorization: Bearer <令牌>`。

### 6.4 静态文件

- 仅放行白名单：`/` `/index.html` `/styles.css` `/app.js`。
- 其余任何路径（含 `.env`、`server.py`、日志、`..` 路径穿越变体）一律 **404**。
- 静态响应带 `Cache-Control: no-cache, no-store, must-revalidate`（改版后普通刷新即生效）。
- 不返回 `Access-Control-Allow-Origin`（同源部署，阻止恶意网页跨域读取看板数据）。

## 8. 安全设计

本项目经过两轮专项安全排查，以下措施均已实现并验证：

| 措施 | 实现方式 | 目的 |
| --- | --- | --- |
| **只读方法白名单** | `call_kw` 校验方法名，非只读方法直接拒绝 | 杜绝通过代理写入/审批 Odoo 数据 |
| **静态文件白名单** | 仅 `/` `/index.html` `/styles.css` `/app.js` 可访问 | 防止 `.env`（含密码）、源码、日志被下载 |
| **默认仅本机监听** | `HOST` 默认 `127.0.0.1` | 防局域网任意设备直接访问 |
| **服务器指纹隐藏** | 覆盖 `Server` 头为 `PurchasingBoard`（无版本号） | 防指纹探测 |
| **API meta 脱敏** | 仅返回 `source` / `updatedAt` | 防泄露数据库名、账号、Odoo 版本 |
| **错误信息脱敏** | 外部仅返回截断概要或统一文案，详情只写服务端 stderr | 防泄露内部路径/堆栈 |
| **去除 CORS** | 不返回 `Access-Control-Allow-Origin` | 防恶意网页跨域读取看板数据 |
| **可选访问令牌** | `BOARD_ACCESS_TOKEN`，`?token=` 或 Bearer 头 | 局域网共享时防越权读取 |
| **本地缓存限时** | localStorage 缓存 7 天过期自动清理 | 防历史业务数据长期残留 |
| **前端 XSS 防护** | 所有动态文本 `escapeHTML()` 转义 | 防注入脚本 |
| **启动信息不打印密码** | 仅打印地址/库名/字段配置 | 防日志泄露 |
| **敏感文件忽略** | `.gitignore` 忽略 `.env`、日志、`__pycache__`、工作笔记 | 防误提交 |

### 遗留建议（可选增强）

- 内网 HTTP 明文传输业务数据 → 建议生产环境启用 HTTPS（如反代）。
- Odoo 侧建议使用**只读专用账号**，不要用管理员账号。
- 如需多人使用且非信任网络，务必设置 `HOST=0.0.0.0` + `BOARD_ACCESS_TOKEN`。

## 9. 部署与运维

### 9.1 环境要求

- Python 3.8+（标准库即可，**无需 pip 安装任何包**）。
- 可访问目标 Odoo 实例（网络可达、账号可登录）。
- 浏览器：Chrome / Edge（推荐，大屏投影优先）。

### 9.2 快速启动

```bat
:: 方式一：Windows 双击
启动.bat

:: 方式二：命令行
python server.py
```

启动成功后浏览器访问 `http://127.0.0.1:<PORT>`（默认端口见 server.py）。

### 9.3 局域网共享

1. `.env` 设置 `HOST=0.0.0.0`；
2. **强烈建议**同时设置 `BOARD_ACCESS_TOKEN=<随机长字符串>`；
3. 其他设备访问 `http://服务器IP:<PORT>/?token=你的令牌`（前端会自动记住令牌）。

### 9.4 常见问题排查

| 现象 | 排查思路 |
| --- | --- |
| 浏览器访问无响应 / curl 返回 000 | 端口可能被残留进程占用：`netstat -ano | findstr <PORT>` 找到 PID 后 `taskkill /F /PID <PID>` 清理，再重启服务 |
| 页面样式/逻辑是旧版 | 服务已返回 no-cache 头 + 资源带时间戳版本号，正常刷新即可；仍旧则 Ctrl+F5 硬刷 |
| API 一直返回 0 条 | 优先检查「紧急字段」识别：Odoo 18 的 `priority` 是 selection 型（值 `"0"/"1"`），确认是否命中字段/选项；可用 `ODOO_URGENT_DOMAIN` 直接指定域验证 |
| 报错「Access Denied」/ 登录失败 | 检查 `.env` 中 `ODOO_USER` / `ODOO_PASSWORD` / `ODOO_DB` / `ODOO_URL` |
| 状态条显示「本地缓存/示例数据」 | Odoo 不可达或拉取失败；服务端日志（stderr）有详细原因 |
| 改 .env 后不生效 | 重启服务；已设置的系统环境变量优先于 .env |

### 9.5 更新发布流程

1. 修改 `server.py` / `index.html` / `styles.css` / `app.js`；
2. 重启服务（先清理占用端口的残留进程）；
3. 浏览器刷新验证；静态资源带 no-cache 头 + 时间戳版本号，无需手工清缓存；
4. 重新打包分发（如需）：参考既有流程用 Python `zipfile` 打包，**排除** `.env`、`.workbuddy`、`*.log`、`__pycache__`，附带脱敏的 `.env.example`。
