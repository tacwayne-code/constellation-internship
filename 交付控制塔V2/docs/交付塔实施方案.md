## 一、实测结论（已连真实库验证）

| 模型 | 有 | 无 |

2. **`purchase.order` 没有 `tag_ids`，但有 `priority`** → 采购紧急用标准 priority 字段

## 二、四需求实现方案（不改 Odoo）

### 需求 1️⃣ 订单标记"普通/紧急"，红色不滥用

**结论：销售订单用 `tag_ids`（crm.tag），生产/采购用标准 `priority`。**

```
销售订单 sale.order          采购 purchase.order       生产 mrp.production
  tag_ids (crm.tag)            priority (0-3)            priority (0-3)
  ├ "紧急"  → 红               ├ 3=紧急 → 红              ├ 3=紧急 → 红
  ├ "非标订单" → 黄            ├ 2=高   → 橙              └ 2=高   → 橙
  └ "普通" → 灰/绿             ├ 1=低                     (排产自动优先!)
                               └ 0=普通
```

- 交付塔前端统一判定：**红色 = (sale 含"紧急"tag) OR (PO/MO priority=3)**
- 防滥用：红色只能通过"打标签"产生，标签由管理员在 Odoo 后台建好；交付塔只读不改
- 前置动作（一次性，在 Odoo 后台或 XML-RPC 创建）：
  - crm.tag：`紧急`、`非标订单`、`普通` 三个标签
  - 在 sale.order 列表页加"紧急"筛选（标准功能，无需开发）

### 需求 2️⃣ 紧急标记自动继承（订单 → 采购）

**不改 Odoo 的实现：交付塔后端调度任务做继承，写回标准字段。**

```
┌─────────┐  定时任务(如5min)  ┌──────────────────────────────┐
│ sale.    │ ──检测─────────→ │ 后端 sync 服务                │
│ order    │   tag含"紧急"     │ 1. 找该 SO 关联的 PO          │
│ tag紧急  │                  │    (sale_line_id 反查)         │
│          │                  │ 2. 若无则按 产品+供应商 匹配    │
│          │                  │ 3. write purchase.order       │
│          │ ←────写回──────── │    priority=3                │
└─────────┘   XML-RPC write   └──────────────────────────────┘
```

- `priority` 是标准字段，`write` 直接可写，**不需要自定义模块**
- 反向同步：采购标记 priority=3 时，若来源 SO 未打 tag，可提示（不强制）
- 此方案把"业务规则"放在交付塔中间层，Odoo 侧零改动

### 需求 3️⃣ 采购看板（全部采购需求 + 颜色区分）

**纯读取，标准字段全可用。**

```python
pol = await client.search_read(
    "purchase.order",
    [["state", "in", ["draft", "sent", "purchase"]]],   # 待办中的采购单
    ["name", "partner_id", "state", "priority",
     "date_planned", "amount_total", "project_id"],
    order="priority desc, date_planned asc",
)
# 前端按 priority 渲染颜色: 3红 / 2橙 / 1蓝 / 0灰
```

- 采购专员视角：只关心「有无采购需求、是否紧急」→ 看板默认按 `priority` 分组（红组置顶）
- 未确认的单（draft/sent）标"待下单"，`state=purchase` 标"已下单"

### 需求 4️⃣ 交付塔（全局状态 + 采购进度 + 物流路由 + 整单 BOM）

**完整数据链路（全部标准模型）：**

```
sale.order (tag_ids, state)
 ├── 外购件 ──→ purchase.order.line.sale_line_id ──→ purchase.order
 │              (qty_received/qty_invoiced)          (state, priority, date_planned)
 ├── 自制件 ──→ mrp.production.origin = SO-xxx ──→ mrp.production
 │              (state, product_qty, qty_producing)   (bom_id, priority)
 │                  └──→ mrp.bom.bom_line_ids ──→ mrp.bom.line (子件清单)
 ├── 库存   ──→ product.product.qty_available / virtual_available
 │              stock.quant (location_id, quantity, reserved_quantity)
 └── 物流   ──→ stock.picking (origin=SO-xxx / project_id)
                 (state, carrier_id, carrier_tracking_ref, scheduled_date)
```

**各视图取数要点**：

| 交付塔视图 | 数据源 | 关键字段 |
|---|---|---|
| 全局状态 | sale.order + 子单聚合 | tag_ids/state |
| 采购下单状态 | purchase.order 按 SO 关联 | state/date_planned/priority |
| 物流路由 | stock.picking + delivery.carrier | carrier_id/tracking/state |
| 整单 BOM | mrp.production → mrp.bom → bom_line_ids | bom_id/bom_line_ids |

**"按订单特殊 BOM"**：标准模型里体现在 **MO（mrp.production）的 bom_id**——每个制造单独立指定 BOM。交付塔展示"该订单实际用的 BOM" = `mrp.production.bom_id` 即可，天然支持订单级差异，无需自定义字段。

**物流路由图**：`stock.move` 的 `location_id → location_dest_id` 是实际物流流向（如 WH/生产前 → WH/生产 → WH/成品 → 客户库位）；delivery.carrier 是运输段。已实测 picking 有 carrier_id 字段可用。

## 五、风险与降级策略

| 风险 | 现状 | 降级方案 |
|---|---|---|
| sale→purchase 反查为空 | sale_line_id 0 条 | ① 产品+供应商名匹配 ② 按 project_id 关联（三模型均有） ③ 空态提示"无采购记录" |
| sale.order 无 priority | 标准如此 | 用 tag_ids；列表/看板按 tag 分组即可 |
| delivery 未实际使用 | 1 承运商 0 关联 | 物流视图退化为 picking 状态流（waiting/assigned/done） |
| 红色滥用 | 无法后端控制 | 标签权限交给管理员；交付塔显示"标签来源"审计 |

---

## 六、一句话总结

> **销售订单紧急 = crm.tag 标签**（sale.order 无 priority 是实测事实）；**采购/生产紧急 = 标准 priority 字段**；**继承规则放交付塔后端定时写回**；**交付塔四链路（采购/生产/物流/BOM）全部走标准模型 XML-RPC，Odoo 零改动**。
